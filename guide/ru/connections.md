# Подключения

В этой главе — виды подключений, вставка строки подключения, SSH-туннель, настройки Patroni и чек-лист готовности. Подключение создаётся и правится в форме: нажмите «+» над деревом подключений или выберите **Изменить подключение** в меню подключения (⋯).

<a id="kinds"></a>

## Виды подключений

В поле **Вид** три значения:

- **Сервер** — один сервер PostgreSQL: хост и порт. В дереве нет группы **Узлы**, а роль сервера, primary или реплика, показана рядом с именем подключения.
- **Список узлов** — несколько серверов (до 16), например primary и его реплики без Patroni. Приложение спрашивает каждый сервер, находится ли он в восстановлении, поэтому primary определяется автоматически, как в JDBC-адресе с несколькими хостами. Если primary нет или их несколько, обзор показывает предупреждение (несколько primary могут означать split-brain). **Узел по умолчанию** задаёт, с какого узла по умолчанию читается каталог: **primary**, **реплика**, **реплика, если есть, иначе primary** или **любой доступный**.
- **Кластер Patroni** — кластер Patroni. Вместо узлов вы указываете от 1 до 8 адресов в поле **Адреса REST API**. Приложение читает участников, их роли, отставание и таймлайн из REST API Patroni и подключается к PostgreSQL каждого участника по адресу, который сообщает Patroni.

Чтобы превратить список узлов в кластер Patroni, отметьте **Узлы под управлением Patroni**: адреса API заполнятся из хостов, с портом 8008.

Узлы опрашиваются раз в 10 секунд. Для списка узлов и кластера Patroni меню подключения позволяет выбрать узел, с которого читается каталог: **Каталог — с узла по умолчанию** или по одному пункту на каждый узел («Каталог — с узла …»). Если выбранный узел станет недоступен, каталог читается с узла по умолчанию, и дерево сообщает об этом.

<a id="connection-string"></a>

## Строка подключения

Вставьте строку подключения в поле **Строка подключения** и нажмите **Заполнить**. Поля формы заполнятся, а строка из поля исчезнет. Понимаются три формата:

- JDBC: `jdbc:postgresql://h1:5432,h2:5433/orders?user=app&targetServerType=primary&ssl=true`
- URI: `postgresql://app:secret@h1,h2:5433/orders?target_session_attrs=read-write&sslmode=verify-full` (подходит и `postgres://`)
- conninfo: `host=h1,h2 port=5432,5433 dbname=orders user=app sslmode=require`

Один хост даёт **Сервер**, несколько хостов — **Список узлов**; кластер Patroni строка не задаёт никогда. У каждого хоста может быть свой порт; иначе берётся общий `port`, иначе 5432. Также заполняются пользователь, база, `sslmode`, файлы CA, сертификата и ключа, таймаут подключения и целевой узел (`target_session_attrs`, `targetServerType`). Строка JDBC с `ssl=true` без `sslmode` означает `verify-full`, как в JDBC-драйвере PostgreSQL.

Пароль из строки попадает в поле пароля и при сохранении подключения записывается в системное хранилище секретов, но не в `connections.json`. Если пароль не сохранён, приложение использует `~/.pgpass`, как `psql`. Unix-сокеты не поддерживаются.

Параметры, которые приложение не использует (`ApplicationName`, `currentSchema`, `options` и другие), пропускаются. Это не ошибка: они перечислены под полем после слов «Не распознано и пропущено».

<a id="ssh"></a>

## SSH-туннель

Если узлы доступны только через бастион (промежуточный хост), включите **Через SSH-туннель** в разделе **SSH**. Тогда все соединения профиля идут через туннель: узлы PostgreSQL, REST API Patroni, проверка подключения.

**Как это работает.** Приложение запускает системный клиент OpenSSH, по одному процессу `ssh` на подключение, с динамическим пробросом (`-D`): это порт SOCKS5, который слушает только 127.0.0.1. Имена узлов разрешает бастион, а не ваш компьютер, поэтому бастион должен видеть узлы по именам, записанным в профиле: хосты, участники Patroni, адреса API. Новым участникам Patroni дополнительная настройка не нужна. Сертификаты TLS проверяются по исходному имени хоста, а не по 127.0.0.1. На бастионе sshd должен разрешать проброс (`AllowTcpForwarding yes`). Своего пароля у порта SOCKS нет: на компьютере, которым пользуются несколько человек (терминальный сервер, общий промежуточный хост), любой вошедший туда может, пока подключение открыто, воспользоваться им и попасть туда же, куда пускают вашу учётную запись на бастионе, поэтому на такой машине пользуйтесь туннелем, только если администратор ограничил проброс на бастионе.

**Поля.**

- **Цель SSH** — имя хоста или алиас из `~/.ssh/config`. Ваш `~/.ssh/config` читается, поэтому работают ProxyJump, SSH-агент, аппаратные ключи и параметры отдельных хостов. Но несколько опций приложение задаёт в командной строке `ssh`, и они главнее файла: `ControlMaster=no` и `ControlPath=none` (туннель никогда не присоединяется к общему соединению), `StrictHostKeyChecking=ask`, `ServerAliveInterval=15` с `ServerAliveCountMax=3`, `NumberOfPasswordPrompts=1`, `BatchMode=no`, `ExitOnForwardFailure=yes` и, для способов **Файл ключа** и **Пароль**, `PreferredAuthentications` (с `IdentitiesOnly=yes`, когда выбран файл ключа).
- **Порт SSH** и **Пользователь SSH** — оставьте пустыми, чтобы взять значения из `~/.ssh/config`. Имя пользователя вводите в поле **Пользователь SSH**, а не как `user@host` в цели; полное имя вида `name@domain` там допустимо. В цели допустимы только латинские буквы, цифры, «.», «_» и «-», в имени пользователя ещё и «@».
- **Вход на бастион** — как входить на бастион:
  - **SSH-агент** — ключи из SSH-агента, включая агентов менеджеров паролей и аппаратные ключи. В приложении ничего не хранится.
  - **Файл ключа** — файл закрытого ключа; выберите его в поле, которое появится ниже. Серверу предлагается только этот ключ. Для зашифрованного ключа введите ещё и **Пассфраза ключа**.
  - **Пароль** — пароль для входа, вводится в поле **Пароль SSH**.

Пассфраза и пароль хранятся в системном хранилище секретов, а не в `connections.json`, файлах экспорта, архиве диагностики и логах.

**Версия OpenSSH.** Для пароля и пассфразы ключа нужен OpenSSH 8.4 или новее: приложение передаёт их через собственный запрос ssh, а более старые клиенты этого не умеют. SSH-агент и ключ без пассфразы работают на любой версии. В Windows 10 встроен OpenSSH 8.1: для пароля и пассфразы установите Win32-OpenSSH 8.4 или новее. Приложение отвечает только на стандартные запросы пароля и пассфразы ключа; одноразовые коды и другие вопросы сервера ответить не могут, поэтому для такого бастиона используйте агент или ключ. Если `ssh` не найден, установите клиент OpenSSH (Windows: дополнительный компонент «Клиент OpenSSH»).

**Первый вход: ключ хоста.** Если ключа бастиона ещё нет в `~/.ssh/known_hosts`, приложение показывает диалог **Неизвестный ключ хоста** с полями **Хост** и **Отпечаток**. Сверьте отпечаток с тем, что дал вам администратор. Кнопка **Доверять и подключиться** повторяет то, что вы делали (подключение, переподключение или проверку), а ключ в `~/.ssh/known_hosts` записывает сам OpenSSH; приложение этот файл не редактирует. Если отказаться, ничему не доверяется.

**Ключ хоста изменился.** Приложение сообщает, что ключ хоста бастиона изменился, и ничего не предлагает нажать: это может быть атака. Уточните у администратора, затем исправьте `~/.ssh/known_hosts` сами, например командой `ssh-keygen -R <хост>`.

**Проверка.** **Проверить** начинается с шага **SSH**: он показывает версию OpenSSH и что туннель поднят. У подключения без туннеля шаг сообщает **Не используется: прямое подключение**.

**Потеря туннеля.** Если процесс `ssh` завершился, например из-за пропавшей сети (обрыв замечается примерно за минуту), подключение получает состояние **Часть узлов недоступна**, узлы за туннелем помечаются недоступными (у кластера Patroni остаются последние известные участники: сам их список приходит через туннель), а приложение перезапускает туннель с паузами 1, 2, 5 и 10 секунд, затем каждые 30 секунд.

Отказ во входе — другое дело. Если бастион отклонил вход (неверный пароль, неподходящий ключ, агент, который в данный момент заблокирован), либо ключ хоста не подтверждён или изменился, либо `ssh` не найден, приложение перестаёт повторять попытки, чтобы не сыпать неудачными входами на бастион. Подключение остаётся в состоянии **Часть узлов недоступна**, пока вы не устраните причину и не выберете **Переподключить** в меню подключения.

**Ошибки.** «Бастион … не смог достучаться до хост:порт» означает, что туннель работает, но этот узел недоступен с бастиона: проверьте, что имя узла разрешается на бастионе и что его порт открыт оттуда. «SSH-туннель к … не работает (локальный порт … отклонил соединение)» означает, что процесс `ssh` только что остановился; приложение перезапустит его, а причина — в подробностях под сообщением. «Не удалось занять локальный порт для SSH-туннеля» — локальный порт оказался занят дважды подряд; повторите попытку.

**Логи.** Вывод каждого процесса `ssh` пишется в `ssh-<id подключения>.log` в папке логов (её путь показан рядом с пунктом **Логи:** на экране **О программе**); `ssh-<id подключения>.1.log` — предыдущий запуск. Оба файла попадают в архив диагностики.

**Ограничение.** Запускайте только одну копию приложения: вторая копия при старте завершает процессы `ssh`, найденные от прошлого запуска, в том числе процессы первой копии.

<a id="patroni"></a>

## Patroni

Для подключения вида **Кластер Patroni** укажите REST API Patroni в поле **Адреса REST API**: от 1 до 8 адресов, начинающихся с `http://` или `https://`, без `user:password@`. Приложение опрашивает их по порядку, пока один не ответит; список участников берётся из `GET /cluster`. Приложение только читает: кластер оно не меняет.

- **Пользователь API** и **Пароль API** — basic-аутентификация, если API её требует. Пароль попадает в системное хранилище секретов. Если все адреса API у вас `https://`, приложение не отправляет пароль участнику, который сообщил адрес `http://`.
- **TLS для API** — настройки TLS для адресов `https://`: файл CA вместо системных корней, проверка имени хоста и клиентский сертификат (PEM или PKCS#12). Клиентский сертификат нужен, если Patroni его требует (`restapi.verify_client: required`).
- **Подмена адресов узлов** — для участников, чьи адреса, сообщённые Patroni, недоступны с вашего компьютера (IP пода, NAT). Для имени участника задайте хост и порт PostgreSQL и адрес его API. За SSH-туннелем имена, которые сообщает Patroni, разрешает бастион, поэтому там подмена обычно не нужна.

В дереве и в обзоре участники показаны с ролями (Leader, Sync, Replica), отставанием и таймлайном. Если API Patroni перестаёт отвечать, приложение продолжает показывать последние известные данные и предупреждение.

<a id="readiness"></a>

## Чек-лист готовности

Нажмите **Проверить** в форме: подключение проверяется без сохранения. Шаги идут один за другим: **SSH**, **Patroni API** (только для кластера Patroni), **Обнаружение узлов**, затем **Узел** для каждого узла (TCP, TLS, вход, версия, роль) и в конце **Готовность**. Упавший шаг показывает ошибку и её подробности; для ошибок SSH это последние строки вывода `ssh`.

Список **Готовность к диагностике** показывает, что приложению нужно для полной диагностики. Каждый пункт имеет статус **Готово**, **Предупреждение** или **Не хватает**, говорит, что перестаёт работать без него, и предлагает точную команду SQL или строку конфигурации для копирования:

- **Роль мониторинга** — роль суперпользователь или член `pg_monitor`. Без неё не видны запросы других пользователей, `pg_stat_statements` и размер `pg_wal`.
- **Отмена и завершение сессий** — членство в `pg_signal_backend`.
- **Обслуживание таблиц** — `pg_maintain` (PostgreSQL 17 и новее); до 17 `VACUUM` и `ANALYZE` работают только для собственных таблиц пользователя.
- `pg_stat_statements` — загружен через `shared_preload_libraries` на каждом узле (нужен перезапуск; в Patroni меняйте через `patronictl edit-config`) и создан в базе командой `CREATE EXTENSION`. Создайте его в каждой базе, где нужен анализ запросов.
- `compute_query_id`, `track_io_timing` и `track_activity_query_size` (не меньше 4096).
- Необязательные расширения, которые дают дополнительные проверки, если установлены: `hypopg`, `pgstattuple`, `pg_buffercache`, `pg_wait_sampling`, `pg_qualstats`, `pg_stat_kcache`.

Если роль мониторинга или роль сигналов отсутствует, раздел **Скрипт роли для диагностики** открывает скрипт, который создаёт роль `glafira_diag`; тот же скрипт есть в руководстве администратора. См. также [Роль для диагностики](getting-started.md#diagnostics-role). Проверка использует собственные короткоживущие соединения к каждому узлу, поэтому оставьте запас в `max_connections` и в лимитах роли.

Подключение работает и без этих пунктов, но недостающие ограничивают то, что приложение может показать.
